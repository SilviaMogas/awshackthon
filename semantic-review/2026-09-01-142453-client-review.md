# Chat client: races, stale state, and lost input across full re-renders

The Health Response Agent browser client is a vanilla-TS SPA where every `store.set()` clears `#app` and rebuilds the whole tree via `mount()`. The chat controller (`callAgent`) drives a request/response loop that pushes user bubbles, a transient "typing" bubble, and agent bubbles into `chatLog`, then re-renders on each step. Consent and escalation flows layer a modal and a polling interval on top of the same store. The full-rebuild model is the root of most problems here: there is no send-in-flight guard, DOM inputs are recreated on every state change, and several pieces of state (`currentQuestion`, `chatLog`) are never bounded or cleared once triage completes.

Watch for: no in-flight guard means rapid sends and double-clicks fire concurrent `callAgent`/escalation requests (confirmed); the composer `<input>` is rebuilt on every re-render so in-progress typing is lost whenever any store change lands mid-typing (confirmed); the provider-contact idempotency key is regenerated on every retry, defeating server-side dedup (confirmed); `currentQuestion` is never cleared after triage, so a free-text message after results is silently swallowed as an answer to the stale question (confirmed); and the follow-up questions render as a redundant one-at-a-time drip (`onset` then `severity` then `sudden_onset` then `progression`) that reads as the same question asked four ways (confirmed).

**Verdict**: NEEDS_CHANGES

## High-level view

There is no concept of "a request is in flight" anywhere in the client. `callAgent`, `performEscalation`, and `performProviderContact` all set `loading: true` but nothing disables the send button, quick-reply chips, or the modal confirm button while awaiting. Because handlers are bound to freshly created DOM nodes on each render and `loading` doesn't gate them, a user (or a double-click) can launch two or more overlapping server round-trips that each push bubbles and stomp each other's `store.set` patches.

The re-render-everything model destroys transient input state. The composer input is a new element on every `store.set` and nothing repopulates it, so text typed while a background render happens (audit refresh, escalation poll, online/offline event) vanishes, and focus is lost after every agent turn.

`currentQuestion` is set from each agent response but never reset to `null` when triage arrives, so the `sendMessage` branch that reinterprets a typed message as an answer to a pending text/number question stays armed after the assessment is done.

The follow-up question flow reads as redundant. `nextFollowUpQuestion` walks a fixed priority list (`onset`, `severity`, `sudden_onset`, `progression`, …) and surfaces exactly one question per round-trip, each rendered as its own agent bubble with its own quick-reply bar. Because `onset` ("When did this start?") and `sudden_onset` ("Did it start suddenly?") both probe timing, and each question arrives with no shared framing, the user experiences three or four near-identical prompts in sequence — the exact "these answers are really redundant" complaint. This is generation/UX, not a race, but it is the most visible behavioral defect in a demo.

Idempotency keys are inconsistent: escalation reuses a stable `dup-<referenceId>` key on retry, but provider-contact mints a fresh `genId("pc")` every call, so retries create duplicate provider requests instead of being deduplicated. The escalation key has the opposite failure mode — it is *too* sticky and can produce false duplicates on a genuinely new escalation.

`chatLog` grows without bound for the life of the session, and the escalation poll interval has cleanup gaps around re-entry and component teardown.

1. **No in-flight guard on send** — `callAgent` never checks or blocks a second concurrent call; rapid Enter presses / double-clicks on send or quick-reply chips fire overlapping requests that push duplicate bubbles and race on `store.set`. Gate on `loading` (and disable the controls) before starting a round-trip.

3. **Provider-contact idempotency key regenerated per call** — `idempotencyKey: genId("pc")` (main.ts:223) is new on every retry, so a retried appointment request is not deduplicated server-side and can create duplicates. Derive a stable key from session + triage requestId.
4. **Stale `currentQuestion` after triage** — never reset to `null` when `res.triage` arrives (main.ts:131); a free-text message sent after results is misrouted as an answer to the old question (main.ts:406). Clear `currentQuestion` when triage completes.
5. **Focus lost after every agent turn** — full `mount()` rebuild drops focus from the composer, forcing the user to click back into the input after each reply. Restore focus post-render on the chat screen.
6. **Quick-reply chips not disabled while loading** — chips are bound to fresh nodes and `showQuick` only hides them when `loading` is already true at render time; a click that fires just before `loading` lands can double-submit an answer. Disable chips on click.
7. **Consent confirm button double-fire** — `onConfirm` is async and the confirm button is not disabled on first click; a double-click runs `performEscalation`/`performProviderContact` twice before `pendingConsent` is cleared. Disable on first click.

9. **Escalation monitor teardown gaps** — the poll keeps firing `store.set` after the user navigates away (`resetAssessment` doesn't clear `monitorTimer`), and a single transient status error silently ends monitoring on a non-terminal status (main.ts:254). Clear on reset/unmount; don't abandon on one failed poll.
10. **Sticky escalation idempotency key** — once `s.escalation` exists, every subsequent escalation reuses `dup-<referenceId>` (main.ts:243), so a new escalation after re-triage collides with the old one and can return a false "duplicate". Incorporate the current triage requestId.

### No in-flight guard: rapid sends and double-clicks launch concurrent round-trips

`callAgent` (main.ts:95–166) sets `loading: true` at the top but never checks whether a request is already running, and no caller checks either. `chatActions.sendMessage`, `answerQuestion`, `runScenario`, `urgentShortcut`, and `submitConcern` all call `callAgent` directly. The send handler in chat.ts (`send()`) clears the input and calls `a.sendMessage(text)` with no guard. Because the button and input are live DOM nodes with no `disabled` state tied to `loading`, two Enter presses in quick succession — or a double-click on ➤, or tapping a quick-reply chip twice — start two overlapping `api.agentMessage` calls.

Each concurrent call independently pushes a user bubble and a typing bubble, then races to `store.set` its own `patch` (agentState, transitions, currentQuestion, triage). Whichever resolves last wins the scalar fields, but both append their agent bubble, so the transcript ends up with interleaved/duplicated turns, and `answers` can accumulate two entries for different questionIds out of order. The typing-bubble lifecycle compounds this: each call captures its own `typingId` and removes only its own, but if call A's response arrives while call B's typing bubble is showing, the ordering of removes vs. pushes is nondeterministic and a typing bubble can be left dangling or a real bubble can land above it.

```
user double-taps ➤
  ├─ callAgent#1  set loading=true, pushTyping(id1) ── await agentMessage ──┐
  └─ callAgent#2  set loading=true, pushTyping(id2) ── await agentMessage ──┤
                                                                            ▼
                              both remove own typingId, both pushChat("agent", …)
                              both store.set(patch)  → last writer wins scalars,
                                                        two agent bubbles appended
```

### Composer input is recreated every render — typed text and focus are lost

The chat input is built fresh inside `chatScreen` on every call (chat.ts, `el("input", {id:"chat-input", ...})`), and `mount()` clears `#app` and rebuilds the tree on every `store.set`. Nothing carries the in-progress `input.value` forward. Any store change that happens while the user is typing — `refreshAudit()` (`store.set({auditEvents})`), an escalation poll tick (`store.set({escalation})`), or an `online`/`offline` event — swaps in a blank input and discards whatever was typed. The same rebuild drops focus, so after every agent reply the user must click back into the field before typing.

`refreshAudit` runs after *every* agent turn and the escalation poll fires every 1600ms while active, so mid-typing wipes are easy to hit in normal use. A targeted fix would preserve `document.activeElement`/selection and the input value across `render`, or exempt the chat input from the blanket rebuild.

### Redundant follow-up questions: one-at-a-time drip of overlapping prompts

`nextFollowUpQuestion` (follow-up.ts) walks a fixed `PRIORITY` list — `onset`, `severity`, `progression`, `sudden_onset`, `associated_symptoms`, `relevant_conditions` — and returns exactly one question. Each `callAgent` round-trip surfaces the next one as a standalone agent bubble (`kind: "question"`) with its own quick-reply bar (`quickReplies` in chat.ts). The `FOLLOW_UP_POOL` text (triage/index.ts) is:

```
onset:        "When did this start?"            [Just now / Today / Yesterday / …]
severity:     "How would you rate the severity right now?"   [Mild / Moderate / Severe]
sudden_onset: "Did it start suddenly?"          [Yes / No]
progression:  "Is it improving, staying the same, or getting worse?"  [Improving / Same / Worse]
```

`onset` and `sudden_onset` are both timing questions, so the user is effectively asked about onset twice, and because every prompt is a bare bubble with no "question 2 of 4" framing or grouping, the sequence reads as the same thing rephrased — the reported "these answers are really redundant." The interaction the user pasted (severity → progression → sudden_onset) is exactly this drip. Concrete fixes, in order of impact:

- Collapse `onset` and `sudden_onset` into one question — e.g. "When and how did it start?" with options "Suddenly, just now / Suddenly earlier / Came on gradually / Had it a while". This removes the duplicate timing probe entirely.
- Batch related questions into a single agent turn. Instead of one round-trip per field, return 2–3 grouped questions (timing + severity + progression) so the user answers a short form once rather than clicking through four separate bubbles.
- Give the sequence context: a lightweight progress indicator ("Question 2 of 4") and distinct bubble framing so consecutive prompts don't feel interchangeable.

This is generation/presentation, not a race, but it is the most visible behavioral defect for anyone walking through the chat.

### Stale `currentQuestion` misroutes post-triage messages

`sendMessage` keys its "treat this as an answer" branch on `s.currentQuestion` being a text/number question (main.ts:406):

```ts
const q = s.currentQuestion;
if (q && (q.answerType === "text" || q.answerType === "number")) {
  // build SymptomAnswer from the typed text, call agent with { answer }
}
```

`callAgent` writes `currentQuestion: res.question` on each turn (main.ts:131) but there is no explicit reset. If the agent's final pre-triage turn was a text/number question and the triage response arrives without overwriting `currentQuestion` to `null` (a `fallback` response, or a triage response that omits `question`), a follow-up free-text message the user types after seeing the result is silently reinterpreted as an answer to the old question rather than a new message. The result card is still shown (`showResult` depends on `s.triage`, not the last bubble), so the user sees results *and* has their next message swallowed into the answered assessment. Reset `currentQuestion: null` whenever `res.triage` is set.

### Idempotency keys: provider-contact regenerated, escalation too sticky

`performProviderContact` mints `idempotencyKey: genId("pc")` (main.ts:223) freshly on every invocation. Combined with the missing in-flight guard and the non-disabled consent confirm button, a double confirm or a retry after a transient failure produces two distinct provider-contact requests with different keys, so server-side idempotency cannot collapse them and the user can be double-booked. Derive the provider key from `sessionId + triage.requestId` so retries are stable.

`performEscalation` has the mirror-image bug: `s.escalation?.referenceId ? \`dup-${s.escalation.referenceId}\` : genId("esc")` (main.ts:243). Once `s.escalation` exists, *every* subsequent escalation reuses `dup-<referenceId>`, so a genuinely new escalation attempt (after symptoms change / new triage) collides with the prior one and may come back as a false "duplicate". The key should incorporate the current triage requestId, not just the prior referenceId.

### Consent confirm can double-fire

`onConfirm` (main.ts:~460) records consent, clears `pendingConsent`, calls `store.set({})`, then awaits `performEscalation`/`performProviderContact`. The confirm button is only `disabled` via `confirmDisabled` (missing required consents), never disabled once clicked. A double-click before the re-render removes the modal runs the whole body twice — two escalations / two provider contacts. Disable the button on first click. (The cancel-then-reopen path is not affected: `recordConsent` de-dupes by `consentType`, so toggling across open/close doesn't accumulate stale records.)

### Escalation poll interval: teardown gaps

`monitorEscalation` (main.ts:254) clears any existing `monitorTimer` before starting, which handles back-to-back calls. Two gaps remain. The interval calls `store.set({escalation: res})` on each tick regardless of what screen the user is now on; if they navigate away (start a new assessment, go to privacy) the timer keeps firing and re-rendering against unrelated screens until it hits `polls >= 4` or an error — and `resetAssessment` does not clear `monitorTimer`. Separately, the `catch` clears the timer on any status error, so a single transient status-endpoint blip ends monitoring silently even though the escalation may still be progressing, leaving the user on a non-terminal status with no further updates.

### `chatLog` grows unbounded

Every turn appends to `chatLog` (main.ts:79, 87) and nothing ever trims it except `resetAssessment`, which starts a whole new session. Within one long conversation (repeated symptom changes, re-triage, back-and-forth), the transcript grows without limit, and since every `store.set` re-maps the entire `chatLog` through `bubble()` and rebuilds the DOM, render cost grows linearly with conversation length. Cap the retained transcript or virtualize the log.

### Number-answer coercion has no NaN guard

`sendMessage` coerces a text reply to a number question with `q.answerType === "number" ? Number(text) : text` (main.ts:406 branch). Non-numeric input becomes `NaN`, which is then sent as the answer; the composer's `send()` blocks only empty/whitespace, so "about five" still produces `NaN`. `questionCard`'s number control (screens.ts) has the same `Number(inp.value)` with no validation. Parse and reject NaN before dispatch.
